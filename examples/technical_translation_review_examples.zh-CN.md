# 技术文档翻译与审查：分层案例

适用模式：`LOOKUP`、`AUDIT`、`BILINGUAL_REVIEW`、`TRANSLATE`；实际修改另按 `REPAIR` 执行。

案例经过抽象改编。产品甲／乙、版本、命令和参数均为示意；给定定义只在对应案例中有效，不代表任何产品的通用结论。

## 分类与检索

按**引发错误的主要机制**归类，再用文档载体和文本角色定位。一个问题可以涉及多个维度，但不要重复报告同一处错误。下列类别用于检索案例，不替代 DBabel 的 `classification`。

| 主类 | 子类与案例 | 优先核查范围 |
|---|---|---|
| [A 上下文与文档层级](#a-上下文与文档层级) | A1 标题与流程冲突；A2 执行范围继承；A3 操作对象错位 | 章节、父子标题、前后步骤、交叉引用 |
| [B 技术语义与逻辑](#b-技术语义与逻辑) | B1 否定与例外；B2 前置条件与顺序；B3 数值单位与统计范围；B4 术语与技术主张；B5 空值与三值逻辑 | 命题、条件、数量、因果与限定范围 |
| [C 产品概念与证据范围](#c-产品概念与证据范围) | C1 跨产品同名概念；C2 版本与旧名称；C3 项目词表与官方标签 | 产品、版本、文档类型、资源适用范围 |
| [D 文本角色与受保护内容](#d-文本角色与受保护内容) | D1 同词异角色；D2 OCR 与可执行字符；D3 占位符与运行值 | 句段、标识符、代码、字符串 |
| [E 文档载体与内容对齐](#e-文档载体与内容对齐) | E1 PDF 阅读顺序与脚注；E2 表格作用域与公式；E3 图形关系与页面对应；E4 HTML 可译边界 | 页面区域、单元格、图形对象、DOM 节点 |

### 核查与标注约定

1. 先恢复结构和源目标对应，再判断词语。检查顺序为：当前片段 → 所属句段／单元格 → 最近小标题 → 上级标题 → 前后同级步骤 → 定义、图注、脚注及引用资料。
2. 文档内先搜索相同对象、操作名称、输入输出文件和相关定义。仍有冲突时，再查适用产品与版本的原始资料。全文出现频率只能提供线索，不能替代证据。
3. 每处修改建议单独定位并记录：`location`、`original`、`recommendation`、`decision`、`reason`、`evidence_refs`。没有实际读到的资料不得作为已读证据。
4. 不确定或冲突未消除的片段标为 `REVIEW`，在 `reason` 写清冲突，在 `next_action` 写清要查哪项资料、确认什么；候选解释不得冒充确定修正。
5. 有充分证据的修改建议标为 `REPLACE`；正确表达用 `KEEP`，字面量用 `PROTECT`。**修改过的内容必须留痕；不确定的内容必须显式标注。**不要把所有修改都标成 `REVIEW`。
6. 实际修复逐处记录 before／after 和执行结果；受保护字面量的修改还需明确授权。标注放在审查表、批注或变更记录中，不插入代码、路径、公式或运行字符串。
7. 以下“验收”均指应执行的检查，不表示已经执行。未读取区域计入 coverage 缺口；未做的视觉或运行检查不得写成 PASS。

## A 上下文与文档层级

### A1 标题写“导出”，实际步骤描述“导入”

**模式：** AUDIT、BILINGUAL_REVIEW。  
**输入：** 技术手册片段；附带的工具说明确认 export_tool 生成归档、import_tool 读取归档并装载目标库。

```text
一级标题：数据迁移
  二级标题：1 源端准备
    三级标题：1.1 导出数据
    操作：从源库生成 archive.bin。
    命令名称：export_tool
  二级标题：2 目标端装载
    三级标题：2.1 数据导出
    操作：读取 archive.bin，将数据写入目标库。
    命令名称：import_tool
```

**问题成因：** 复制上一节的小标题后未更新，或步骤被移动后标题与正文脱节；不能仅凭表面词义断定是哪一处错了。

**排查与判断：**

1. 确认 2.1 的父标题是“目标端装载”，不是仍属于“源端准备”。
2. 跟踪同一文件：1.1 生成 archive.bin；2.1 读取该文件。比较动作的起点、终点与输入输出。
3. 对照本例提供的工具说明，核查命令实际承担的动作；不能只凭工具名称猜功能。
4. 搜索同章步骤表、图注和交叉引用，检查是否有第二次导出、回滚或校验分支。流程不必按“导出—导入”交替。
5. 记录支持“导入”的证据及仍然冲突的小标题；如资料仍不足，保留原文并请求针对性确认。

**处置：** 2.1 小标题标 `REVIEW`；提出候选“数据导入”，说明需确认标题是否复制错误。命令名称 `PROTECT`，不把 import_tool 改成 export_tool。得到源文更正依据或明确确认后，才对该标题提出 `REPLACE`；同步检查目录和引用该标题的位置，逐处留痕。

**验收：** 说明“为什么怀疑标题”，列出父标题、数据流及命令依据；不能只写“上一步导出，所以下一步必然导入”。只有英文把正确的“数据导入”错译成 Export 时，才直接按源目标不一致提出译文修正。

### A2 上级标题涵盖两台主机，不等于每一步都执行两次

**模式：** BILINGUAL_REVIEW。  
**输入：**

```text
一级标题：配置主机 A 与 B
  二级标题：3.1 通用准备
  范围：在 A、B 分别创建目录。
  二级标题：3.2 主机 A 初始化
  范围：仅在 A 执行。
  步骤：生成实例文件，然后同步到 B。
  随附文件清单：instance/config/、instance/data/、instance/control/
```

待审译文把 3.2 写成“Initialize the instance on both hosts”，并把同步对象概括成“configuration files”。

**问题成因：** 只沿用一级标题的范围；又把目录名误当作内容类型。

**排查与判断：**

1. 将每步绑定到最近明确的执行范围：3.1 为 A、B；3.2 为 A。上级标题提供任务范围，不覆盖更具体的局部限定。
2. 区分“在哪里执行同步命令”和“文件到达哪里”：B 是接收端，不自动成为初始化步骤的执行端。
3. 读取给定文件清单，确认同步对象包含数据与控制文件；不只看路径名称猜测。
4. 在源目标对应中检查执行主机、身份、对象和顺序是否完整保留。

**处置：** “on both hosts”→“on host A only”，`REPLACE`；“configuration files”→“instance files”，`REPLACE`，必要时按原清单列出范围。若没有清单，只保留中性的“files in the specified directory”，对内容性质标 `REVIEW`。这不是部署正确性认证。

**验收：** 没有新增 B 上的初始化步骤；同步路径不变；每处范围修订均有记录。若源文没有“仅在 A”且上下文互相矛盾，不按常见部署经验自行补出答案。

### A3 标题、按钮与正文指向不同操作对象

**模式：** AUDIT、SOURCE_RESEARCH。  
**输入：**

```text
章节：查询缓存管理
小标题：清理当前会话缓存
按钮：Clear session cache
说明：此操作会删除当前表空间。
```

**问题成因：** 可能误贴其他章节的说明，也可能有未说明的副作用。单词各自正确，组合后却描述了不同对象：缓存与表空间。

**排查与判断：**

1. 抽取“动作—对象—范围”：清理／缓存／当前会话，与删除／表空间／当前对象。
2. 在同一文档搜索完整异常句，判断是否从“存储管理”章节复制；搜索命中只说明可能来源，不证明该句一定应删除。
3. 查同版本该按钮的帮助、操作说明与影响范围；核对按钮属于哪个页面和对象。
4. 分别排除标题错、按钮错、正文错三种可能。资料无法排除时，不直接按多数文本统一。

**处置：** 异常说明标 `REVIEW`，明确问“实际影响是会话缓存还是表空间”。取得同范围直接依据后，才修改错误位置；不为了让句子通顺而悄悄改成“清理缓存”。

**验收：** 报告说清是哪两个操作对象冲突、查过哪里、还缺哪项证据；不执行按钮或删除命令来验证翻译。

## B 技术语义与逻辑

### B1 否定、例外与“全部”同时丢失

**模式：** BILINGUAL_REVIEW。  
**输入：** 已批准源文：

> Unless all replicas have acknowledged the record, the coordinator must not mark it as committed.

待审译文：

> 只要任意副本确认该记录，协调节点就可以将其标记为已提交。

**问题成因：** 将 unless 误读为普通条件，将 all 缩小为任意一个，又把禁止条件转成充分条件。

**排查与判断：**

1. 单独标出量词 all、否定 must not、例外 unless，以及动作 mark as committed。
2. 还原源文约束：“未全部确认时，不得标记为已提交。”全部确认只是移除这条禁令，原句没有证明它是唯一提交条件。
3. 用两个情形比对：仅一个副本确认、全部副本确认。检查译文是否新增许可。
4. 回查 committed 的定义或项目词表，避免把“已提交”改成“已持久化”等不同状态。

**处置：** 译文整句 `REPLACE` 为“除非所有副本均已确认该记录，否则协调节点不得将其标记为已提交。”分别说明否定、量词和条件方向的错误。术语依据不足时，对状态名称另列 `REVIEW`，不妨碍指出逻辑错误。

**验收：** 不把“只有满足条件才可能执行”改写为“满足条件就一定执行”；不据此声称某数据库实际使用该协议。

### B2 把前置校验移到操作之后

**模式：** BILINGUAL_REVIEW。  
**输入：**

源文：“备份成功且完整性校验通过后，方可移除临时副本。”  
待审译文：“Remove the temporary copy after the backup completes, and then verify its integrity.”

**问题成因：** 为简化长句重排动作，丢失“成功”和“校验通过”两个门槛；it 还可能指向已移除的副本。

**排查与判断：**

1. 拆成三个事件：备份成功、完整性校验通过、移除临时副本。
2. 建立先后关系：前两者必须先满足，第三者才被允许；完成不等于成功。
3. 查相邻步骤确认校验对象，是备份产物还是临时副本。原文未明确时，不靠代词就近原则猜测。
4. 若同节明确写“校验备份产物”，在译文中用 backup 消除歧义；否则单列对象歧义。

**处置：** 在校验对象已确定为备份产物的条件下，`REPLACE` 为“Remove the temporary copy only after the backup has succeeded and passed the integrity check.” 若对象不明，顺序错误可指出，校验对象另标 `REVIEW`。

**验收：** 不改变操作次序，不把“校验已运行”当作“校验通过”；不新增源文未要求的实际备份或删除操作。

### B3 数值相同，单位、默认值与作用范围已经变了

**模式：** BILINGUAL_REVIEW。  
**输入：** 参数表及注释：

| 参数 | 默认值 | 单位 | 作用范围 | 特殊值 |
|---|---:|---|---|---|
| retry_wait | 500 | ms | 每次重试 | 0 表示不等待 |

待审译文：“The connection timeout is 500 seconds. A value of 0 disables retries.”

**问题成因：** 参数名与相邻连接设置混淆；表头单位在抽取时丢失；“不等待”被扩写成“取消重试”。

**排查与判断：**

1. 将同一行的数值、单位、范围和特殊值重新绑定，不能只抽取 500。
2. 区分等待间隔、连接超时、总重试时长；不能因位置相邻就认作同一指标。
3. 把默认值与固定上限分开；把 0 的特殊语义与功能开关分开。
4. 若允许改写单位，需证明换算正确并留痕；参数值本身不能随正文换算自动修改。

**处置：** `REPLACE` 为“The default wait per retry is 500 ms. A value of 0 means no wait.” 另对参数名 `PROTECT`。若源表与注释给出不同单位，先 `REVIEW`，查适用版本的参数定义。

**验收：** 值、单位、默认属性、每次范围及 0 的含义全部一致；数字相等不能单独判定通过。

### B4 术语修正与性能主张分别处理

**模式：** AUDIT、CLAIM_ROUTE。  
**输入：** 项目词表规定“事务处理速率”使用 transaction throughput。待审句：

> Our transaction speed is twice that of the baseline, with no data loss.

只提供了术语表，没有测试方法、负载、硬件、故障条件或测量结果。

**问题成因：** 把术语顺畅误当作事实可靠；润色时可能进一步扩大“无数据丢失”的承诺。

**排查与判断：**

1. 分开定位术语 transaction speed、倍数比较 twice、保证性主张 no data loss。
2. 术语按已批准词表处理；保留原倍数含义，不能把 twice 写成增加 200%。
3. 对倍数和保证分别说明需要什么证据；不能用词表支持测试结论。
4. 检查原始材料是否有适用负载、同步模式、故障范围等限定，防止漏译或移出有效范围。

**处置：** 术语 `REPLACE` 为 transaction throughput；两个事实主张分别 `OUT_OF_SCOPE_CLAIM`，classification 为 `TECHNICAL_CLAIM`，明确 next_action。若用户另要求事实核查，按独立证据任务处理；未核实前不强化，也不自行删除原主张。

**验收：** 每个问题有独立位置与决策；修改术语的记录不写成“性能和可靠性已验证”。

### B5 NULL、空字符串与“未知”被混成一个概念

**模式：** LOOKUP、BILINGUAL_REVIEW。  
**输入：** 本例已读、适用的参数与 SQL 说明规定：NULL 与空字符串不同；标量值的普通等号比较涉及 NULL 时结果为 unknown。待审译文：“NULL 表示空字符串，因此 NULL = NULL 为真。”

**问题成因：** 把自然语言的“空”映射到多个不同技术概念；将日常“相同东西相等”的直觉套入 SQL 三值逻辑。

**排查与判断：**

1. 分别列出 NULL、空字符串、数字 0、文本字符串 `'NULL'`，查明材料讨论的数据类型与产品范围。
2. 对照给定定义，区分缺失值、已知的零长度字符串和普通字符串文本；不要只用一个“空值”统称。
3. 确认使用的是普通等号还是专门的空值判断／空值安全比较；不同运算不能互相代替。
4. 将三种真值 true、false、unknown 分开。这里普通等号比较结果不是 true，也不能简单改成 false。
5. 若文档涉及特殊兼容模式、复合值或另一产品，重新核查对应语义，不推广本例结论。

**处置：** 在给定范围内，将译文 `REPLACE` 为“NULL 不等同于空字符串；使用普通等号比较 NULL 时，结果为未知。”保留 SQL 标记，不把说明审校扩展成查询重写。产品范围或运算符不明时，相关概念判断 `REVIEW`。

**验收：** 能说清“哪一种空”“哪一种比较”；不把 unknown 译成 false，不给 NULL 加引号变成字符串，不宣称所有数据库对空字符串的处理都相同。

## C 产品概念与证据范围

### C1 相同术语在不同产品中对应不同层级

**模式：** LOOKUP、AUDIT。  
**输入：** 对比文档附两份已读、适用的产品定义：

| 资料范围 | 给定定义 |
|---|---|
| 产品甲 | schema 在相关创建语句中与 database 表达同一对象 |
| 产品乙 | 一个 database 包含多个 schema；schema 内组织表等对象 |

待审文档把两列 schema 都解释成“独立数据库”，并宣称两种对象可以一一对应迁移。

**问题成因：** 将一个产品中的命名规则当作跨产品通用定义，又将术语近似推成实现等价。

**排查与判断：**

1. 按列绑定产品和版本，禁止给整张表只分配一个产品范围。
2. 比较定义、包含关系、命名空间及访问边界；词形相同不证明层级相同。
3. 将“如何称呼”与“迁移是否一一映射”分开，后者需要额外的对象与迁移规则证据。
4. 检查图例、列标题和脚注是否已有区分，不为统一译词抹掉差异。

**处置：** 产品乙列“独立数据库”的解释 `REPLACE` 为“数据库内组织对象的命名空间”。产品甲列按其给定定义保留。对迁移等价主张 `OUT_OF_SCOPE_CLAIM`；不自动转换建库、建模式语句。

**验收：** 概念关系写出适用范围；不建立无证据的全局 `synonym_of` 映射。只知道两者“用途相近”时，不能升级为等价。

### C2 新版改名，不代表旧版参数可以直接替换

**模式：** AUDIT、SOURCE_RESEARCH。  
**输入：** 文档明确适用于版本 1。附带资料规定：

| 版本 | 命令／参数 |
|---|---|
| 版本 1 | 使用 OLD_SOURCE |
| 版本 2 | 引入 NEW_SOURCE，并将 OLD_SOURCE 标记为弃用 |

待审稿把版本 1 的所有 OLD_SOURCE 改为 NEW_SOURCE，理由是“统一最新术语”。

**问题成因：** 只搜索最新页面；把弃用、移除、别名和可执行语法更新混为一谈。

**排查与判断：**

1. 先确定目标文档版本，再读取对应版本条目；发布时间较新不等于更适用。
2. 核对名称变化是正文称呼、UI 标签还是可执行 token，三者不能自动同步替换。
3. 分辨 deprecated 与 removed；即使新版仍接受旧名，也不能反推旧版支持新名。
4. 若任务明确要求升级文档，另核查升级目标的参数语义和兼容性，不把语言审查扩展成迁移验证。

**处置：** 对版本 1 原始参数 `PROTECT`；对未经依据的替换提出恢复建议，并标识受保护字面量。版本不明确则 `REVIEW`，先补适用范围；不能以“最新”作为 HIGH confidence 的理由。

**验收：** 所用证据的版本匹配明确；历史版本资料可作为该版本的 CURRENT 证据；没有静默更新命令。

### C3 正文项目用语与精确 UI 名称不必相同

**模式：** BILINGUAL_REVIEW。  
**输入：** 本次范围明确的三项资料：

- 项目词表：说明性正文中的“目标数据库”使用 target database。
- 同版本英文 UI：对应选项卡名称为 Destination。
- 中文源文：“在‘目标’选项卡中选择目标数据库。”

待审译文：“Select the target database on the Target tab.”

**问题成因：** 全局词表覆盖了精确 UI 名称；同一个汉语词的两次出现实际承担不同角色。

**排查与判断：**

1. 将引号内选项卡名与正文概念分开，分别绑定 UI 记录和词表。
2. 按界面位置、控件功能与版本匹配，不能只在英文截图中搜索一个相似单词。
3. 查清 UI 记录是否实际打开；项目约定不能自动充当厂商界面证据。
4. 若已存在准确译文，保留它，不为了单词一致把两个角色强行统一。

**处置：** Target tab 中的 Target `REPLACE` 为 Destination；target database `KEEP`。未取得 UI 记录时，标签 `REVIEW`，正文仍可按项目词表处理。

**验收：** 译文为“Select the target database on the Destination tab.”；修改只作用于对应控件标签。项目选择不被标记为官方通用名称。

## D 文本角色与受保护内容

### D1 同一词形分别是概念、列名和业务数据

**模式：** TRANSLATE、BILINGUAL_REVIEW。  
**输入：** 任务要求仅翻译解释文字，保留 SQL。源片段：

```text
将记录提交后，再读取 status 列。业务状态名称见下方查询。
SELECT status FROM job_log WHERE status = '已提交';
```

待审译文把 status 列改成 state，把字符串“已提交”改成 committed，并将正文“提交”写成“标记业务状态”。

**问题成因：** 未区分事务动作、列标识符和应用自行定义的状态值；把同名词当成同一数据库概念。

**排查与判断：**

1. 区分三个角色：正文操作、SQL 标识符、字符串数据。
2. 查询源文的事务说明与业务状态定义，确认“提交”指哪个对象；不能用状态值的字面含义解释事务行为。
3. 比对 SQL token 和字符串内容，检查是否因英文化改变查询条件。
4. 即使字符串看起来可翻译，也先看它是否参与程序匹配；解释性译名放在正文或词表中。

**处置：** status 与原字符串 `PROTECT`；对目标 SQL 的变动逐处标注，建议恢复字面值，实际恢复需字面量修改授权。正文已有明确事务依据时提出 `REPLACE`；定义不足则 `REVIEW`。

**验收：** 不把“还有中文”直接判成漏译；不混同事务提交与业务状态；不执行 SQL 证明翻译。

### D2 OCR 可疑字符不能靠常见拼写补齐

**模式：** AUDIT、BILINGUAL_REVIEW。  
**输入：** 扫描文档抽取得到 `RETRY_L1MIT=10`，图片中的 I、l、1 难以辨认；目标译文自动改成 `RETRY_LIMIT=10`。

**问题成因：** OCR 将相似字符混淆；语言模型按熟悉单词补正，掩盖来源不确定性。

**排查与判断：**

1. 返回原页对应区域查看字符，记录可辨识程度，不能只对 OCR 结果做拼写检查。
2. 文档内检索同一参数的定义表、其他出现位置、示例输出；多个 OCR 副本不算多个独立证据。
3. 查同产品同版本参数资料，区分“原页确实这样写”与“产品允许这样写”两个问题。
4. 原页明确使用错误参数时，报告源文错误；原页仍不可辨认时，报告抽取不确定。两者不能合并成已证实修正。

**处置：** 可疑参数 `REVIEW`，同时 protected=true；列出候选字符及所需清晰原图／版本资料。证据明确后才提出字面量修正；未授权前不应用。数值 10 同样不得顺手更改。

**验收：** 能区分 OCR 错误和源文错误；原图未读清的区域计入覆盖缺口；不以语料常见度作为参数有效性的证据。

### D3 占位符名称保留了，但位置对应关系被交换

**模式：** BILINGUAL_REVIEW。  
**输入：** 本例资源说明：`{source}` 和 `{target}` 是命名占位符，分别注入源端与目标端名称。

源文：“从 {source} 向 {target} 复制 {count} 条记录。”  
待审译文：“Copy {count} records from {target} to {source}.”

**问题成因：** 词序调整时交换了占位符的语义位置；仅检查占位符集合会误判通过。

**排查与判断：**

1. 校验名称、大小写、出现次数及括号；再比较每个占位符绑定的语义角色。
2. 将 from／to 与源／目标对应，不能因为三个占位符都还在就结束检查。
3. 阅读格式引擎约定，区分可重排的命名占位符与依赖顺序的位置参数。
4. 不使用实际客户值填充模板，也不改占位符键名来“修复方向”。

**处置：** 译文 `REPLACE` 为“Copy {count} records from {source} to {target}.”；占位符键名 `PROTECT`。若模板引擎约定未知，不能擅自重编号参数，相关部分标 `REVIEW`。

**验收：** 集合、数量、类型约束和语义位置均一致；记录方向修正，不能只记录“占位符检查通过”。

## E 文档载体与内容对齐

### E1 PDF 抽取顺序打乱，脚注中的适用条件消失

**模式：** BILINGUAL_REVIEW、AUDIT。  
**输入：** 双栏技术手册左栏写“支持在线操作¹”，右栏属于另一节；页脚 ¹ 写“仅适用于指定存储模式”。抽取文本把右栏接到左栏句后，并遗漏页脚。译文因此变成无条件支持在线操作。

**问题成因：** PDF 字符存储顺序不等于阅读顺序；抽取器未覆盖脚注，限定范围随之消失。

**排查与判断：**

1. 对照页面图像恢复栏位、标题边界和脚注锚点；不要把抽取文本直接视为连续正文。
2. 将主句与脚注作为一个语义单元对齐到译文，确认脚注限定的是哪项功能。
3. 区分“只漏翻脚注”“脚注有译文但锚点丢失”“脚注在文件中却未显示”。
4. 看不清脚注时记录位置和缺口，不能自行补成常见限制。

**处置：** 原脚注清楚且任务允许修订时，提出恢复脚注及对应锚点的建议并留痕；无法辨认则 `REVIEW`、coverage=PARTIAL。恢复限定不等于验证产品能力，事实真实性另行界定。

**验收：** 页面阅读顺序、脚注文字与锚点同时复核；只验证正文文本存在，不能判定版式和语义完整。

### E2 合并表头与公式让“空白格”失去含义

**模式：** BILINGUAL_REVIEW。  
**输入：** 电子表格 B1:C1 合并为“主节点”，D1:E1 合并为“备节点”；第二行是“单位”“默认值”。译文把 C 列数值划入备节点，并把公式 `=Config!B3` 替换为当前显示值。

**问题成因：** 按单元格逐个抽取，丢失合并表头作用域；把公式结果误当作静态文本。

**排查与判断：**

1. 恢复合并区域和多级列头，将每个值绑定到角色、单位、字段三元组。
2. 空白单元格可能继承上方合并标题，也可能真实为空；仅在结构支持时继承。
3. 分别读取公式和显示值；检查文本改动是否误伤工作表引用、命名范围或数据验证。
4. 批注、隐藏行和嵌入对象只在实际可读取时计入覆盖；不能默认它们不存在。

**处置：** 错误角色归属提出 `REPLACE`；公式 `PROTECT`，已被替换的目标单元格单独记录恢复建议。无法读取的批注或嵌入说明列为缺口，相关判断 `REVIEW`。

**验收：** 表头层级、行列绑定、公式及引用保持正确；数值显示相同不足以证明文件完整。

### E3 图中主备角色互换，单词都正确仍然是错译

**模式：** BILINGUAL_REVIEW。  
**输入：** 技术演示文稿中，节点 N1 标“主节点”，N2 标“备节点”，箭头从 N1 指向 N2。英文稿的 Primary、Standby 拼写正确，但分别贴在 N2、N1；另一页又复用了本页截图。

**问题成因：** 将标签脱离图形对象翻译；根据左右位置或相似缩略图分配目标页，忽略节点身份与页面差异。

**排查与判断：**

1. 用页码、图形对象、节点 ID 和连线端点建立对应，不仅用“左图／右图”。
2. 核对角色标签、箭头方向、图注所描述的数据流，不能靠英文词表检查代替关系检查。
3. 比较两页源图的独有对象或状态，确认是真实重复还是不同步骤；源页重复本身不一定有错。
4. 检查组合图形、母版文字及文本溢出，防止文字存在却覆盖了相邻标签。

**处置：** 按源图身份提出逐标签的 `REPLACE`；重复错图提出页面对应修正。缺少源图或无法确认节点时标 `REVIEW`，不能按惯例认定左主右备。

**验收：** 角色、节点、连线和页面对应全部一致；实际编辑后必须回看渲染结果。仅提取到 Primary、Standby 两个词不能证明图正确。

### E4 HTML 属性有些可译，有些承担程序绑定

**模式：** TRANSLATE、BILINGUAL_REVIEW。  
**输入：** 任务允许翻译用户可见文字、title 和 aria-label；链接与程序标识符保持原样。

```html
<a id="retry-link" href="#retry-policy"
   title="查看重试规则" aria-label="查看重试规则">重试规则</a>
<span translate="no">EXAMPLE_MODE</span>
```

目标稿把 href 改成 `#重试规则`，遗漏 aria-label，并将 EXAMPLE_MODE 译成自然语言。

**问题成因：** 只看页面可见文字，或反过来把所有属性都视为可翻译文本。

**排查与判断：**

1. 按 DOM 节点和属性角色建立可译边界：正文、辅助说明与功能标识符分别处理。
2. 读取 translate 标记及继承范围，并核对任务是否明确覆盖该标记；本例没有覆盖。
3. 保留 href、id 及其绑定关系；只有用户要求链接本地化且目标映射可验证时，才另行处理。
4. 对照可见文字与无障碍标签，检查其中一处是否遗漏；显示正确不等于所有目标文本已译。

**处置：** 文本、title、aria-label 在授权范围内翻译为一致的 Retry policy 等表达；id、href、EXAMPLE_MODE `PROTECT`。目标稿已破坏的绑定与标识符逐处标注恢复建议。无法确认链接目标或标记含义时 `REVIEW`。

**验收：** DOM 结构、链接锚点和保护字符串保持一致；可译属性未遗漏；没有用正则全局替换修改脚本、样式或标识符。

## 输出要求

沿用 DBabel 的 [报告约定](../references/11_OUTPUT_AND_DATA_CONTRACTS.md)；案例分类只用于说明问题来源，正式 finding 使用现有分类与决策。

- 将同一段中的术语错误、事实主张和未决歧义拆开，各自定位。
- 把原文错误、译文错误、抽取错误、版式呈现错误区分开；它们可能同时出现。
- `REVIEW` 项必须说明已经查到的上下文和仍缺失的决定性证据，不能只写“请人工检查”。
- 所有修改建议、实际修改和未决项都能回到原位置；相同词的多个出现位置分别记录。
- 没有修复请求时 repair 为 `NOT_REQUESTED`；尚未应用的修复方案为 `PROPOSED`。不将候选建议写成 `APPLIED` 或 `VERIFIED`。
- 修复完成后，按 [QA 要求](../references/08_QA_AND_RELEASE_GATES.md) 回读与检查；可读内容完整不等于全部证据充分，也不等于视觉检查完成。
- 正确且适用的译文保留为 `KEEP`。取消一项关键证据后，应重新判断，不能机械沿用案例答案。
